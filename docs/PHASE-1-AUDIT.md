## Current architecture and module inventory

| Module | Responsibilities and principal dependencies |
| --- | --- |
| Authentication/profile | `AuthController`, `User`, password broker, sessions, login/reset throttles, hashed password cast. No public registration route. |
| Roles and administration | Three roles: Owner, Office Manager, Bookkeeper. `config/rbac.php`, permission/role seeders, `UserController`, `ActiveAccount`, role/permission middleware, policies and `Access`. Owners/managers see permitted firm-wide records; bookkeepers generally see assigned clients. |
| Overview/navigation | `DashboardController`, `Summary`, onboarding/completeness calculators, role-aware dashboard, sidebar, search, notifications, firm settings. |
| Clients/onboarding | `ClientController`, `Client`, assignment/archive/restore, client detail, organization onboarding list and checklist, justified exemption for clients without configured requirements. Completion is separate from operational status. |
| Documents | `DocumentController`, `Document`, private uploads/downloads, review/approval/rejection/clarification, protected replacement of reviewed attachments. |
| Requirements/missing documents | `RequirementController`, `RequirementTemplateController`, `MissingDocumentsController`, `DocumentCompleteness`; client requirements, periodic/onboarding scope, templates, document links, follow-ups. Uploads and expectations are different business concepts. |
| Chart and templates | `AccountController`, `AccountTemplateController`, `ChartOfAccounts`, `TemplateManager`, per-client accounts, versioned templates, initialization, fiscal years/periods. |
| General Journal | `/ledger`, `LedgerController`, `LedgerEntry`/`LedgerItem`, `JournalWriter`, eligibility/review/evidence/posting services. Draft → review → posting; correction path, independent reviewer, review digest and retained evidence. |
| Vouchers | `VoucherController`, `VoucherWriter`, `Voucher`; JV/CV/CR/CD identities and printouts attached to the same underlying journal, not an independent ledger. |

| Financial reports | `FinancialReportController`/service: trial balance, income statement, balance sheet and account ledger. Balance sheet requires a fiscal year containing its reporting date. |
| Billing/payments | `InvoiceController`, `PaymentController`, `Invoice`/`InvoiceItem`/`Payment`, draft/open/cancel workflow, balance-derived payment statuses, locked payment writes, print/PDF. Firm billing is separate from client bookkeeping. |
| Compliance | `ComplianceController`, `ComplianceRecord`, `DeadlineCalculator`, internal submission and official filing deadlines, monitoring, per-client checklist and follow-ups. |
| Knowledge Base | `KnowledgeController`, `KnowledgeArticle`, `KnowledgePolicy`; drafts/publication, categories/tags, author restrictions. Retain this module. |
| Operational reports | `ReportController`, `Records`, `Display`, `Summary`; filtered module tables, CSV export with formula-injection mitigation, page print. Different purpose from financial statements. |
| Notices | `NoticeController` and policy; management publication/archive workflow. Bookkeepers are intentionally denied notices under current grants; confirm business intent before changing. |
| Audit/backup | `Audit`, `AuditLogController`, `AuditLog`; private backup services/commands and restore verification. Scheduled deadline notifications in `routes/console.php`; backup schedule is documented but not scheduled there. |

Generic CRUD uses `Modules` → `ModuleController` → `RecordRequest`/`RecordInput` → `RecordWriter`, with shared records views. Financial services provide stronger domain boundaries. Route binding of `{record}` depends on the route-name prefix and `Modules`; changes to route names must preserve this contract.

Core relationships: user belongs to role, role has permission pivot; client owns documents, requirements, accounts, fiscal years/periods, journals, invoices and compliance records. Journal owns lines and retained document evidence and has one voucher. Invoice owns items/payments. Requirement links documents through a unique document pivot and owns follow-ups. Audit rows reference users/clients and a module/record identifier. Many business models use soft deletes; client archive instead changes status.

## Ranked findings

Severity reflects likely impact; source findings do not imply exploitation or corrupted live data.

| ID | Severity / evidence | Finding and required action |
| --- | --- | --- |
| A01 | High, source-confirmed | `RequirementController::index`, `periodOptions`, and `MissingDocumentsController::index` fetch accounting periods with clients without `Access` scoping. Both index views render every period's client business name. Assigned-client bookkeepers can therefore receive other clients' names/period labels. Scope options by accessible client IDs; add negative response tests for unassigned names and IDs. |
| A02 | High, source-confirmed | `ComplianceController::monitor` paginates 15 rows before applying deadline filters to the current collection. Matching records on later pages are missed and paginator totals remain unfiltered. Filter the full authorized result before pagination; cover matches beyond page 1 and counts. |
| A03 | High operational, reproduced | The configured application MySQL service is unreachable. End-to-end behavior against existing firm records cannot be verified. Restore connectivity without database initialization/reset, then run read-only migration/integrity checks and take verified backups. |
| A04 | High operational, reproduced | `ZipArchive` is unavailable in this PHP CLI. Attachment backup test fails, so a full recovery set cannot currently be created by the file command. Composer does not explicitly require `ext-zip`. Check web and CLI PHP separately, declare/preflight required extensions, then rehearse backup/restore. |
| A05 | High test-isolation risk, source-confirmed | `BackupStore::basePath()` uses the application's real storage path. `BackupTest` changes the source disk but does not isolate backup destinations; successful backup tests can prune old manifests/artifacts. Future baseline runs must isolate `LARAVEL_STORAGE_PATH` as well as the database. The full MySQL follow-up in this audit uses isolated storage. No backup pruning was observed in the default SQLite run: its database backup rejects memory and file backup fails before pruning. |
| A06 | Medium, source-confirmed | `Completed` compliance semantics differ: `Summary` excludes it from pending, dashboard deadlines and `Records` overdue filter exclude only `Filed`, and ordinary validation requires filing date/reference only for `Filed`. Moving Filed → Completed also clears `filed_date` in `RecordWriter`. Define terminal states and whether completion requires filing; preserve prior filing evidence and use one predicate across views/notifications. |
| A07 | Medium, source-confirmed | `prepareComplianceDeadlines` checks an explicitly submitted internal date against filing date, but preserving an old manual override when the filing date changes bypasses that comparison. An earlier filing date can leave submission after filing. Revalidate final effective dates under the write lock; add a regression for this case. |
| A08 | Medium integrity risk, source-confirmed | Requirements use independent period/client FKs, and update validation only compares ownership when a new `client_id` is submitted. Updating just `accounting_period_id` can bypass the same-client check. Model validation protects client changes only when documents exist. Resolve effective client on update; add forward composite ownership constraint after checking historical rows. Also revalidate linked document period compatibility when requirement periods change. |
| A09 | Medium, reproduced | Seven baseline assertions depend on the old six-client sample dataset; `SampleDataSeeder` now creates eighteen clients and corresponding invoices/compliance/journals. This produces 18 vs 6 and 117,000 vs 39,000 failures. Separate deterministic test fixtures from expanded demo data; preserve access-denial assertions instead of merely loosening counts. |
| A10 | Medium, reproduced | `DemoDeploymentTest` directly queries `sqlite_master`; the MySQL runner's initial Voucher filter selects this test and stops on it before the full regression/browser stages. Make trigger inspection driver-aware or explicitly scope that scenario to SQLite, then retain a real MySQL equivalent. |
| A11 | Medium workflow gap | `SampleDataSeeder` creates For Review journals with name-only lines, no account ownership references, period or retained evidence. `is_legacy` blocks editing and posting requires complete mapping. Demo queues therefore contain work that cannot complete through ordinary workflow. Keep historical records; use valid separate demo fixtures and design an explicit audited legacy reconciliation workflow. |
| A12 | Medium workflow gap | Payment correction/refund/reversal and period close/reopen administration have no routes in the inspected route set. Posted entries are immutable and there is no dedicated linked reversal action. Do not weaken immutability: specify correction authority, original-reference links, period rules and audit history before implementing. A manual compensating journal may already serve part of the accounting purpose. |
| A13 | Medium security hardening | `AuditLog` is ordinary mutable Eloquent storage without append-only model/DB protection. Several follow-up/template writes record audit separately from the data mutation. DB access or audit-write failures can compromise evidence completeness. Use transactions for paired writes, restrict runtime DB privileges and define tamper-resistant retention. No web audit edit/delete route was found. |
| A14 | Medium environment boundary | `AccountingSchema::installsTriggers` permits skipping protection whenever both demo flags are enabled, including a production environment. Existing export includes triggers, but newly migrated demo databases may not. Add deployment/readiness checks that prohibit this configuration for real business data; flags alone do not prove installed triggers. |
| A15 | Low/medium scalability and UX | Several client/document selectors truncate at 500; onboarding and missing-document monitoring load whole authorized collections before manual pagination. Larger firms can lose selectable items or incur slow requests. Use permission-scoped searchable selectors and measured query pagination without changing readiness definitions. |
| A16 | Low, source-confirmed | Sidebar `clients.*` also matches onboarding, and `compliance.*` also matches monitoring; both base and specialized entries can be active simultaneously. Requirement template/index entries also share active states. Group navigation and make active selection exclusive. |
| A17 | Low maintenance | CDN Bootstrap/fonts and public assets coexist with an unused-looking Vite/Tailwind pipeline. Do not delete it merely from package presence; establish the actual asset build contract, offline behavior and CSP/integrity strategy first. `report.print` is enforced by financial report, ledger and voucher print endpoints; billing print/PDF currently authorize invoice visibility only. Confirm whether billing print/export requires separate privileges. |

No verified critical vulnerability or wrong posted financial total was demonstrated. Billing line arithmetic currently converts quantity and price to cents, multiplies and rounds; journal/report services use integer cents and overflow checks. Billing SQL status calculations use a separate `SUM(ROUND(quantity * unit_price,2))` expression. Boundary rounding agreement, very large aggregates, duplicate payment submissions, payment dates before invoice dates, tax meaning (amount versus rate), and fiscal close/earnings conventions need independent financial fixtures. Billing/payment controllers do not automatically create client journal entries; this may be correct because firm receivables and client books are different entities. Confirm ownership before designing any integration.

## Database/security safeguards to preserve

Accounting migrations `2026_10_10_000001` through `000007` establish templates, client-owned accounts, fiscal ranges, journal ownership, evidence, immutability and vouchers. Preserve decimal storage, composite client ownership FKs, positive/balanced line validation, closed-period checks, client → journal lock order, review digests, retained file hashes, voucher uniqueness and triggers. Existing accounting migration rollback guards intentionally refuse destructive rollback with financial data. Use new forward migrations, never edit applied migrations to retrofit live databases.

Authentication already has guest/auth boundaries, active-account checks, rate limits, session regeneration, password hashing, password reset token rotation/session invalidation and last-active-owner protection. RBAC is checked in policies and field-level write authorization, not just hidden buttons. CSV formula injection is mitigated; uploads are private and permission-gated. These controls are valuable and must remain covered by tests. Default development seed passwords are public in source but seeders are environment guarded; never run development seeders on firm data. No actual production account credential audit was possible.

Read-only checks after database connectivity is restored: pending migrations, installed triggers/check enforcement, posted debit/credit equality, missing account/period ownership, overpayments/nonpositive payments, requirement/document/period cross-client links, orphan references, overlapping fiscal ranges, missing attachment/evidence files and hashes, archived-client visibility, terminal compliance evidence, submission after filing, and least-privilege runtime grants. Measure legacy exclusions before claiming statements represent all historical activity.

## Safe backup procedure before implementation

1. Restore normal connectivity to the existing server; verify resolved database/host and do not initialize a new database in its place.
2. Verify PHP ZIP support, dump binary, free disk and restricted backup directory ACLs. Preserve the desktop export unchanged as a historical copy, not a verified recovery set.
3. Use `veritas:backup:database` and `veritas:backup:files --include-public` after reviewing retention: the commands prune old backup sets. For a pre-refactor archive, use a dedicated archive location or preserve existing backups before invoking retention. Coordinate a quiet write window for a consistent DB/attachment pair; include triggers and privately escrow the application key/config needed for recovery.
4. Record SHA-256, sizes, source commit/schema, timestamp and both artifacts. Encrypt an approved off-host copy; do not put records or secrets in Git.
5. Restore only into a fresh disposable server/database and staging file directory. Review SQL for embedded `USE`/database creation. Validate counts, FK ownership, installed checks/triggers, evidence hashes and representative accounting balances, not only successful import.
6. Existing `docs/BACKUP-AND-RECOVERY.md` is a useful runbook. Backup scheduling is currently provisional; assign ownership, retention and recovery targets. No live backup or restore was performed during this audit.
