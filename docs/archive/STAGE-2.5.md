# Stage 2.5 completion report

Increment 2, Stage 2.5 implements the read-only General Ledger and shared accounting balance calculation foundation. No Increment 3 financial statements have been implemented.

1. **Features implemented.** Authorized client/account selection, inclusive date filters, account code/name/classification, inactive account history, opening balance, period debits and credits, net movement, closing balance, ordered journal movements, running balances, pagination carry-forward, source journal navigation, empty states, responsive presentation, and selected-page browser printing. Peso amounts retain their actual debit/credit direction, including unusual balances. The reusable service also returns balances for all accounts of an authorized client, including zero-balance accounts.

3. **Calculation methodology.** The authoritative Posted scope supplies journal lines with matching journal, line, and account client ownership. Entire journals with unmapped lines are excluded, including partially mapped legacy entries. Opening is posted debits minus credits strictly before the start date. Period movement is debits minus credits from start through end, inclusive; closing is opening plus movement. Ordering is calendar transaction date, journal ID, then line ID. A single ordered financial SELECT supplies each account request's summary, row count, page carry, and visible movements. Previous-page movements contribute to every subsequent running balance. Shared `balances()` uses the same accumulator across client accounts. No balances are persisted, and no dashboard figures participate.

   Individual stored amounts are read as decimal text and converted to integer cents. MySQL uses its existing DECIMAL storage. SQLite's numeric affinity is accommodated by formatting each permitted two-decimal line amount before conversion; there is no floating-point total or SQL SUM. Calendar-date normalization avoids SQLite's midnight suffix changing inclusive boundaries. Checked signed-integer addition/subtraction rejects overflow before committing accumulator changes. Dr/Cr formatting handles even the minimum signed integer without `abs()` overflow.

4. **Routes and permissions.** `GET /general-ledger` (`general-ledger.index`) and `GET /general-ledger/print` (`general-ledger.print`) use existing authenticated, active-user and role middleware. The `generalLedger` policy requires an existing supported accounting role and `bookkeeping.view`, `account.view`, and `client.view`; existing client-assignment rules apply. Printing additionally requires `report.print`. The service itself authorizes access and refetches accounts within the selected client. Forged client/account pairs are rejected. No new permission grants were introduced.

9. **Remaining limitations.** Each calculation scans the relevant posted history through the end date; there is no materialized balance, cache, or high-volume performance benchmark. The cursor limits model hydration, but PDO may buffer results. Each request reads current posted data: new or backdated postings between pagination or print requests can change totals; this is not a frozen multi-request snapshot. Printing explicitly covers the selected page with full-period summary and page carry; no full-ledger CSV/PDF export is included. The default current calendar month is a filter convenience, not a fiscal-year rule. Opening-balance imports, legacy mapping, adjusting/reversal workflows, fiscal conventions, and production rollout remain separate scope. Chapter 3's detailed report layouts and conventions were not supplied with this approval and must be reconciled before report acceptance.
